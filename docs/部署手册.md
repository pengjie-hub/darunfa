# 从零部署手册 —— 小发智购（仿大润发电商系统）

> 目标：把本地项目部署成 **https://你的域名/app/**（或 `http://服务器IP/app/`）这样一个可以直接写进简历、招聘方点开就能用的在线演示。
>
> 环境假设：阿里云**中国香港**轻量应用服务器 2核4G / Ubuntu 24.04，域名免备案。
> 总耗时：**首次约 3~4 小时**（其中构建等待约 15 分钟，其余是操作与排错）。

---

## 0. 部署后的架构长什么样

```
                    DNS: 你的域名（可选）→ 服务器公网 IP
                              │
                        ┌─────▼──────┐
   浏览器 ── 443/80 ──▶ │   Nginx    │  宿主机，Let's Encrypt 证书
                        │  (host)    │  负责 HTTPS 终止 / gzip / 静态缓存
                        └─────┬──────┘
                              │ proxy_pass 127.0.0.1:8080
                        ┌─────▼──────────┐
                        │  app 容器       │  Spring Boot 4 fat jar
                        │  Java 17 / 8080 │  内含 Vue 后台(/app/) + 旧后台(/admin.html)
                        └─────┬──────────┘
                              │ JDBC（compose 内网，不暴露公网）
                        ┌─────▼──────┐
                        │  mysql 容器 │  MySQL 8.0，数据在具名卷 mysql-data
                        └────────────┘
```

**关键设计**：只有 Nginx 暴露公网端口；app 绑在 `127.0.0.1:8080`；MySQL 完全不映射端口。这样即使应用有未授权访问漏洞，数据库也不会直接暴露。

## Stage 0 · 修三个必须先修的坑

### 0.1 吊销泄露的 DeepSeek API Key（**最高优先级**）

`backend/src/main/resources/application.properties` 里原本有一把明文的真实 key，而且这个文件已被 Git 跟踪（提交 `ca4796d` 起就在）。只要仓库推到 GitHub 或服务上了公网，key 会在数小时内被自动化爬虫扫走并刷额度。

**代码侧已经改好了**，现在读的是环境变量：

```properties
deepseek.api-key=${DEEPSEEK_API_KEY:}
```

`DEEPSEEK_API_KEY` 是 Spring 松绑定能自动识别的标准名（`DEEPSEEK_API_KEY` → `deepseek.api-key`），所以写成这副样子**不是必须的** —— 不写这行，环境变量照样能覆盖。显式保留占位符是为了两件事：让「key 只能来自环境变量」在配置里看得见，以及末尾的空默认值让启动报错变成一句中文说明而不是 `Could not resolve placeholder`。

你还需要做两件事：

1. 打开 <https://platform.deepseek.com> → API keys → **把旧的 `sk-4fa6…` 删掉**。代码里删掉了不代表它已经作废，只要它还有效就一直有被盗刷的风险。
2. 新建一把 key，**只填进服务器的 `deploy/.env`**，不要写回代码。

> 本地想在 IDEA 里跑：Run Configuration → Environment variables 加上 `DEEPSEEK_API_KEY=sk-xxx`。
> 没设时启动会直接失败并提示「DeepSeek API Key 未配置」——这是刻意的 fail-fast，不是 bug。
> 如果你在系统里另有 `DEEP_SEEK_API_KEY`（带下划线）这个变量，它**不会**被识别，请以 `DEEPSEEK_API_KEY` 为准。

### 0.2 种子数据 SQL（**已处理，无需操作**）

`docs/darunfa_seed_20261101.sql` 是 11 月 1 日的导出，内容本身干净（首行就是 `-- MySQL dump`）。但更早的 `docs/darunfa_seed_20261023.sql` 开头 15 行混进了当时 mysqldump 在 PowerShell 里的报错输出（`mysqldump.exe : ... NativeCommandError`），直接导入会在第一行报 `ERROR 1064`。

部署用的是已整理好的版本，**随仓库提供**：`deploy/sql/01-darunfa-seed.sql`（207,172 字节 / 25 张表 / 24 条数据插入）。MySQL 容器首次启动、数据卷为空时会自动导入它。

**你不需要跑任何命令。** 只有当源文件更新了、需要重新导出时才要执行：

```bash
bash deploy/scripts/prepare-seed.sh
```

> Windows 上如果提示 `bash: 未找到命令`，那是因为 cmd/PowerShell 的 PATH 里没有 bash。
> 用 Git 自带的：`"C:\Program Files\Git\bin\bash.exe" deploy/scripts/prepare-seed.sh`
> 注意要在这个 worktree 目录（`...\Worktrees\darunfa\feature-vue-admin-0781f852`）下执行，
> 桌面那份 `Desktop\darunfa` 里没有 `deploy` 目录。

### 0.3 修掉前端构建脚本的路径 bug（已改好，了解即可）

原来的 `npm run build:backend` 是这条命令：

```json
"build:backend": "vite build --base=/app/ --outDir=../backend/src/main/resources/static/app"
```

在 **Windows 的 Git Bash 下它会产出坏掉的 HTML**：MSYS2 会把以 `/` 开头的命令行参数当成文件系统路径转换，`--base=/app/` 被转成 `C:/Program Files/Git/app/`，于是 `index.html` 里的资源引用变成 `src="C:/Program Files/Git/app/assets/index-xxx.js"` 这种绝对盘符路径，部署后所有 js/css 必然 404。

**已修复**：新增 `frontend/vite.config.backend.js`，把 `base` 与 `outDir` 写进配置文件（不经过 shell 参数转换），`build:backend` 改为 `vite build --config vite.config.backend.js`。

验证方式：

```bash
cd frontend && npm run build:backend
grep -E 'src=|href=' ../backend/src/main/resources/static/app/index.html
```

必须看到 `/app/assets/...`（以 `/app/` 开头），不能出现 `C:/` 或 `C:\`。

> 顺带说明：Docker 镜像构建走的是另一条路（Linux 环境下 `--base=/app/` 没有路径转换问题），所以镜像里不依赖这个修复。两条路都能产出正确结果，本地开发用 `build:backend`，部署用镜像。

### 0.4 推送到 GitHub

服务器上要用 `git clone` 拉代码，所以先有一个远程仓库（顺便也是简历上的代码链接）。

```bash
# 在项目根目录
git remote add origin https://github.com/你的用户名/darunfa.git
git branch -M main
git push -u origin main
```

> 如果仓库想设为 Private，服务器上 clone 需要配置 Deploy Key（`ssh-keygen` 生成后加到仓库 Settings → Deploy keys，只读权限即可）。

**别忘了**：`.gitignore` 里加一行 `deploy/.env`，确保真实密钥永远不进仓库（这个仓库的 `.gitignore` 已加）。

## Stage 1 · 买服务器与域名

### 1.1 服务器

推荐配置（阿里云轻量应用服务器，**中国香港**地域）：

| 项 | 推荐值 | 说明 |
|---|---|---|
| 规格 | 2核4G / 80G ESSD | 2核2G 也能跑，但要按附录 A 调内存 |
| 带宽 | 30Mbps 峰值 / 3072GB 月流量 | 套餐自带，个人演示绝对够 |
| 镜像 | Ubuntu 24.04 LTS | 比 Alibaba Cloud Linux 生态资料多，排错好搜 |
| 价格 | ¥804/年，300 元学生券抵扣后约 ¥504/年 | 折合 ¥42/月 |

购买时注意三点：

1. **地域选香港**，创建后**不可修改**，公网 IP 也不支持解绑更换。
2. 300 元学生券在**支付页面**确认可抵扣；官方规则写的是"适用于部分公共云产品"，若香港地域不可用，退单改买大陆地域（但要接受备案流程）。
3. 记住 root 密码，或购买后立即在控制台重置。

### 1.2 域名（**可选**）

**不想买域名可以直接跳过本节**，用 `http://服务器公网IP/app/` 访问，后续 Stage 5 走"方案 B"。代价是没有 HTTPS、浏览器显示"不安全"。

如果要买：

- 在阿里云「域名」注册（`.com` 约 ¥60/年首年，`.top/.xyz` 更便宜）
- 注册后到「云解析 DNS」加一条 **A 记录**：`@` → 服务器公网 IP，TTL 600
- 再加一条 `www` → 同一个 IP（可选）
- 香港服务器**不需要 ICP 备案**，解析生效即可访问

> 域名解析生效通常 10 分钟内。可以先用 `ping 你的域名` 确认解析到的 IP 对不对。

### 1.3 安全组 / 防火墙

在轻量控制台「防火墙」放行：**22（SSH）、80（HTTP）**，有域名并要上 HTTPS 时再加 **443**。
不要放行 8080 和 3306——它们只在服务器内部用。

## Stage 2 · 服务器初始化

登录服务器（Windows 用 PowerShell 或 Git Bash 都行）：

```bash
ssh root@你的服务器IP
```

依次执行：

```bash
# 1. 系统更新
apt update && apt upgrade -y

# 2. 时区（订单时间、AI 统计都依赖这个）
timedatectl set-timezone Asia/Shanghai
date   # 确认输出 CST

# 3. 加 2G swap —— 容器构建阶段内存吃紧，swap 是保险丝
fallocate -l 2G /swapfile
chmod 600 /swapfile
mkswap /swapfile
swapon /swapfile
echo '/swapfile none swap sw 0 0' >> /etc/fstab
free -h   # 应看到 Swap: 2.0Gi

# 4. 基础工具
apt install -y git curl vim ufw

# 5. 主机防火墙（与云控制台安全组是两层，都要配）
ufw allow 22/tcp
ufw allow 80/tcp
ufw allow 443/tcp
ufw --force enable
ufw status
```

## Stage 3 · 装 Docker、放代码、配密钥

### 3.1 装 Docker

```bash
curl -fsSL https://get.docker.com | sh

docker --version           # Docker version 2x.x.x
docker compose version     # Docker Compose version v2.x.x
systemctl enable --now docker
```

> 如果 `curl get.docker.com` 慢，可换阿里云镜像：把 `https://get.docker.com` 换成
> `https://get.docker.com | sed 's|download.docker.com|mirrors.aliyun.com/docker-ce|' | sh`，
> 或在 `/etc/docker/daemon.json` 配置 `registry-mirrors`。

### 3.2 拉代码

```bash
mkdir -p /opt && cd /opt
git clone https://github.com/你的用户名/darunfa.git
cd /opt/darunfa
```

### 3.3 配密钥（**这一步最关键**）

```bash
cp deploy/.env.example deploy/.env
vim deploy/.env
```

四个值都要改：

```ini
MYSQL_ROOT_PASSWORD=换成你自己的强密码（建议纯字母数字）
JWT_SECRET=用 openssl rand -base64 48 生成
ADMIN_PASSWORD=后台管理员初始密码
DEEPSEEK_API_KEY=sk-你新申请的key
```

> 这行没填的话，`docker compose up` 会直接报错并提示「请在 deploy/.env 中设置 DEEPSEEK_API_KEY」，不会等到部署完了才发现 AI 调不通。

生成 JWT_SECRET：

```bash
openssl rand -base64 48
```

### 3.4 准备种子数据（无需操作）

种子 SQL 已随仓库提供，`git clone` 下来就在，直接确认一下存在即可：

```bash
ls -lh deploy/sql/     # 应有 01-darunfa-seed.sql，约 225K
```

如果这一步文件不在（比如你 clone 的是旧提交），才需要生成一次：

```bash
bash deploy/scripts/prepare-seed.sh
```

## Stage 4 · 构建并启动

```bash
cd /opt/darunfa/deploy
docker compose up -d --build
```

首次构建要做三件重活，**耐心等 8~15 分钟**：

1. `npm ci` 装前端依赖（约 400 个包）
2. `mvn dependency:go-offline` 拉 Maven 依赖（含 BGE 中文嵌入模型，约 160MB）
3. `mvn package` 打包

构建过程中可以另开一个终端看进度：

```bash
docker compose logs -f app
```

### 4.1 确认启动成功

```bash
docker compose ps
```

期望看到两个容器都是 `running`，且 mysql 是 `healthy`。

```bash
docker compose logs --tail=60 app
```

日志里要能看到这几行（顺序可能不同）：

```
HikariPool-1 - Start completed.
Tomcat started on port 8080 (http)
Started BackendApplication in xx.xxx seconds
```

### 4.2 本机验证（还没配 Nginx，先用 8080）

```bash
curl -I http://127.0.0.1:8080/login.html        # 期望 HTTP/1.1 200
curl -I http://127.0.0.1:8080/app/              # 期望 200（Vue 后台外壳）
curl -s http://127.0.0.1:8080/api/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"admin","password":"admin123"}' | head -c 300
```

第三条如果返回带 `token` 的 JSON，说明**应用 + 数据库 + 鉴权链路全通了**。

> 注意：种子数据里已存在 `admin` 账号（密码 `admin123`），而 `DataInitializer.initAdmin()` 的逻辑是"账号已存在就跳过"。所以 `deploy/.env` 里的 `ADMIN_PASSWORD` 在导入种子数据的情况下**不会生效**。这是预期行为，不是 bug。

## Stage 5 · Nginx + 访问入口

> **两条路，先选一条：**
> - **A · 有域名** → 能做 HTTPS，简历上是 `https://xxx.com/app/`，观感最好
> - **B · 无域名** → 用 IP 访问 `http://1.2.3.4/app/`，**没有 HTTPS**，浏览器会显示"不安全"
>
> 两条路只有 Nginx 配置和一个证书步骤不同，应用本身完全一样。**可以先走 B 跑通，以后再补 A**——换配置 + 一条 certbot 命令即可，不用重新部署。

### 5.1 装 Nginx 与 Certbot

```bash
apt install -y nginx
apt install -y certbot python3-certbot-nginx     # 走方案 B 可以不装
```

### 5.2 配站点

**方案 A（有域名）：**

```bash
cp /opt/darunfa/deploy/nginx/darunfa.conf /etc/nginx/sites-available/darunfa.conf

# 把 your-domain.com 换成你的真实域名
sed -i 's/your-domain.com/你的域名/g' /etc/nginx/sites-available/darunfa.conf

ln -sf /etc/nginx/sites-available/darunfa.conf /etc/nginx/sites-enabled/
rm -f /etc/nginx/sites-enabled/default

nginx -t          # 必须显示 syntax is ok / test is successful
systemctl reload nginx
```

**方案 B（无域名，纯 IP）：**

```bash
cp /opt/darunfa/deploy/nginx/darunfa-ip.conf /etc/nginx/sites-available/darunfa.conf

# 不需要改任何内容：server_name 已用 _ 兜底，listen 带 default_server
ln -sf /etc/nginx/sites-available/darunfa.conf /etc/nginx/sites-enabled/
rm -f /etc/nginx/sites-enabled/default         # 必须删，否则 default_server 冲突

nginx -t && systemctl reload nginx
```

先用 HTTP 验证一次：

```bash
curl -I http://你的域名/app/          # 方案 A
curl -I http://服务器公网IP/app/      # 方案 B
```

> 如果这一步不通，**先别签证书**。先排查：域名解析对不对（`ping 你的域名`）、安全组 80 端口开了没、`ufw status`、`nginx -t`。
> 方案 B 排查顺序：安全组 80 放行 → `ufw status` → `curl -I http://127.0.0.1:8080/login.html`（确认应用本身活着）→ `nginx -t`。

### 5.3 签 HTTPS 证书（**仅方案 A**）

```bash
certbot --nginx -d 你的域名 -d www.你的域名 \
  --agree-tos -m 你的邮箱 --redirect --non-interactive
```

`--redirect` 会自动把 HTTP 跳到 HTTPS。certbot 会自动改 Nginx 配置并装好续期定时器。

验证：

```bash
curl -I https://你的域名/app/
certbot renew --dry-run      # 演练续期，看到 success 就行
```

> 方案 B 跳过这一步。**原因不是"懒得配"**：Let's Encrypt 必须校验域名所有权，纯 IP 签不了证书。自签证书浏览器会红字警告，比 http 更难看。

### 5.4 最终访问路径

| 方案 A（有域名） | 方案 B（纯 IP） | 内容 |
|---|---|---|
| `https://你的域名/` | `http://服务器IP/` | 302 跳转到 `/app/` |
| `https://你的域名/app/` | `http://服务器IP/app/` | **Vue 3 新后台**（简历主推） |
| `https://你的域名/admin.html` | `http://服务器IP/admin.html` | 旧版单文件后台 |
| `https://你的域名/login.html` | `http://服务器IP/login.html` | 旧版登录页 |

> 方案 B 的代价，你自己权衡：
> - 浏览器地址栏会显示"不安全"，面试官点开第一眼就能看到
> - 登录密码、JWT 走明文 HTTP，**别在演示站放真实个人信息**
> - 好处是省钱（域名约 ¥30-60/年）、省事，且随时能补

## Stage 6 · 验收清单

按顺序点一遍，全绿才算部署完成。建议边点边截图，这些截图后面直接放简历/答辩 PPT。

### 6.1 基础链路

- [ ] `https://你的域名/app/`（或 `http://服务器IP/app/`）能打开
  - 有域名：浏览器地址栏是**小锁图标**（证书有效）
  - 纯 IP：会显示"不安全 / Not secure"，**属预期**，不影响功能
- [ ] 用 `admin / admin123` 能登录，登录后停在仪表盘
- [ ] 刷新页面（F5）不会 404（哈希路由生效）
- [ ] 浏览器控制台（F12）**没有红色报错**，Network 里没有 4xx/5xx

### 6.2 业务功能（挑重点点）

- [ ] 仪表盘：4 个图表有数据（近 7 天销售趋势 + 订单/分类/支付分布）
- [ ] 商品管理：列表有数据、能搜索、能编辑
- [ ] 订单管理：列表分页正常、能看详情、能发货（运单号自动生成）
- [ ] 库存管理：低库存预警能看到
- [ ] 促销管理 / 分类管理：增删改正常
- [ ] 会员管理：列表有数据
- [ ] 权限管理：角色与权限码显示正常

### 6.3 AI 功能（这个项目最大的亮点，必须验）

- [ ] 右下角 AI 运营助手能对话，问「今天有多少订单」能返回**真实数字**（说明工具调用通了）
- [ ] 评论管理 → 点某条评论的 🧠 按钮 → 返回情感标签（正面/中性/负面/投诉）+ 紧急度
- [ ] AI 知识库页面能搜索，返回相关规则片段（说明 RAG 向量检索通了）
- [ ] AI 回复草稿能生成，内容里**没有承诺赔偿/免单**这类越界表述

> AI 首问会比较慢（10~30 秒，模型要思考 + 走工具调用），第二次就快了。这是正常的，不是卡死。

### 6.4 安全

- [ ] 有域名：`http://你的域名` 自动跳 `https://`；纯 IP：无此项，直接访问即可
- [ ] 未登录直接访问 `/app/#/products` 会被踢回登录页
- [ ] 用普通运营账号登录，看不到「角色管理 / 权限管理」（`adminOnly` 生效）
- [ ] 纯 IP 方案额外确认：**没把真实个人信息填进会员/地址数据**（HTTP 明文传输）

## Stage 7 · 日常运维

### 7.1 更新代码（最常用）

改完代码推到 GitHub 后，在服务器上：

```bash
cd /opt/darunfa/deploy && ./deploy.sh
```

脚本会做：`git pull` → 重建镜像 → 重启 → 轮询健康检查 → 打印状态。

### 7.2 看日志

```bash
cd /opt/darunfa/deploy
docker compose logs -f app          # 实时跟
docker compose logs --tail=200 app  # 看最近 200 行
journalctl -u nginx -n 50           # Nginx 日志
tail -f /var/log/nginx/darunfa.error.log
```

### 7.3 数据备份（每天自动一次）

```bash
mkdir -p /opt/backup
cat > /opt/backup/backup.sh <<'EOF'
#!/usr/bin/env bash
set -euo pipefail
cd /opt/darunfa/deploy
set -a; . ./.env; set +a
STAMP=$(date +%F)
docker compose exec -T mysql \
  mysqldump -uroot -p"$MYSQL_ROOT_PASSWORD" --single-transaction --routines darunfa \
  | gzip > /opt/backup/darunfa-$STAMP.sql.gz
# 只保留最近 7 天
find /opt/backup -name 'darunfa-*.sql.gz' -mtime +7 -delete
EOF
chmod +x /opt/backup/backup.sh

# 每天 03:30 跑
( crontab -l 2>/dev/null; echo '30 3 * * * /opt/backup/backup.sh' ) | crontab -
```

### 7.4 演示环境被搞乱了？一键重置

## 附录 A · 2核2G 机器的内存调优

如果只买了 2G 内存，改三处，否则容易被 OOM Killer 杀掉进程：

**1. `deploy/docker-compose.yml` 里 MySQL 内存**

```yaml
- --innodb-buffer-pool-size=192M    # 原 384M
- --performance-schema=OFF
```

**2. 应用 JVM 上限**（同文件 app 服务）

```yaml
environment:
  JAVA_OPTS: "-Xms128m -Xmx640m -XX:+UseSerialGC -Duser.timezone=Asia/Shanghai"
```

**3. 构建阶段不要在服务器上构建**

2G 机器跑 `mvn package` 大概率 OOM。改为本地构建后上传 jar：

```bash
# 本地（Windows Git Bash / macOS）
cd frontend && npm ci && npm run build:backend && cd ..
cd backend && ./mvnw -DskipTests package && cd ..

# 上传
scp backend/target/backend-0.0.1-SNAPSHOT.jar root@服务器IP:/opt/darunfa/app.jar
```

然后 compose 里 app 服务改成直接挂载 jar、不用 build（把 `build:` 段删掉，`image:` 换成 `eclipse-temurin:17-jre-jammy`，`volumes` 挂 `/opt/darunfa/app.jar:/app/app.jar:ro`）。

**4. 再加 2G swap**（Stage 2 已做，2G 机器建议加到 4G）

## 附录 B · 常见故障速查

| 现象 | 大概率原因 | 怎么查 / 怎么修 |
|---|---|---|
| 浏览器 502 Bad Gateway | app 容器没起来或崩了 | `docker compose ps` 看状态；`docker compose logs --tail=100 app` |
| 容器启动几秒就退出 | `.env` 缺值 或 MySQL 没 healthy | 日志里会有 `Could not resolve placeholder` / `Communications link failure` |
| 页面空白、控制台 404 找 js | 前端 base 路径不对 | 检查 `static/app/index.html` 里的引用是否以 `/app/` 开头；出现 `C:/` 说明用了旧构建命令 |
| `/app/` 打开是 Spring 的 404 页 | 前端产物没打进 jar | `docker compose exec app ls /app` 看不到 static；检查 Dockerfile 的 `COPY --from=web` |
| 中文全是问号/乱码 | 数据库字符集 | 确认 MySQL 启动参数有 `--character-set-server=utf8mb4`；导入时用 `SET NAMES utf8mb4` |
| AI 接口返回 401 | DeepSeek key 错或过期 | `docker compose exec app env \| grep DEEPSEEK`（确认注入的是你新申请的那把） |
| AI 接口 504 / 超时 | Nginx 超时太短 | 已设 `proxy_read_timeout 180s`；确认没被前面别的配置覆盖 |
| AI 返回"余额不足" | DeepSeek 没钱了 | 充值（这就说明费用护栏生效了） |
| 首次请求 AI 特别慢 | RAG 模型首次加载 | 正常，第一次要加载 ONNX 模型，之后常驻内存 |
| `docker compose build` 卡住 | 拉依赖慢 | 换镜像源，或改成本地构建上传 jar（附录 A-3） |
| 域名打不开但 IP 能开 | DNS 未生效 / 安全组没开 80 | `ping 域名`；控制台防火墙；`ufw status` |
| certbot 报 challenge 失败 | 80 端口被占或被拦 | 确认 `systemctl status nginx`、安全组 80 放行、域名已解析 |
| MySQL 数据没了 | 用了 `docker compose down -v` | `-v` 会删具名卷，这是不可逆的；用 Stage 7.4 的重置流程前先备份 |
